# TerraMind AI — Annotation Specification: Image-Specific Visual Observations

**Version:** 1.0 (Stage 2B)
**Scope:** how to collect genuine, image-specific text observations for the 17,870 eligible PlantWild images so that the text-only baseline and the early/intermediate/late fusion models can be trained and compared validly.
**Non-goals:** this document does not create data and does not authorize training. No observation text may be generated from disease labels, class names, or `plantwild_prompts.json`.

## 1. Objective and experimental role

The experiment compares image-only, text-only, early-fusion, intermediate-fusion, and late-fusion systems on the **same** duplicate-free eligible samples and the same official train/validation/test boundaries. The text modality must carry information about **the specific image** (symptoms actually visible in that image), not the class it belongs to. Any text that encodes the target label is invalid and is rejected by the loader.

## 2. Eligibility and required coverage

The annotation population is exactly the `eligible_by_split` set in `outputs/research/fusion_eligibility_manifest.json`:

| Split | Eligible images | Min per class | Median per class |
|---|---:|---:|---:|
| train | 12,573 | 32 | 139 |
| validation | 1,751 | 4 | 19 |
| test | 3,546 | 8 | 40 |

Every class has at least 4 eligible images in every split, so annotating all eligible images yields complete class coverage without touching official splits. Duplicate-group members excluded by the manifest are **not** annotated.

## 3. Blinding (annotators must not see the target)

PlantWild paths embed the class name (e.g. `apple scab/1.jpg`), so paths, filenames, folder names, class lists, and class-conditioned prompts all leak the label. Therefore:

- Annotators work only against **opaque aliases** (`obs-` + 12 hex chars) generated by `scripts/build_annotation_workbook.py`.
- Images are presented by alias with **no filename, no folder, no EXIF, and no metadata panel**.
- The alias → image mapping is written to a **sealed** file (`outputs/annotation/sealed/alias_map.json`) that is never shared with annotators or stored alongside the workbook.
- Annotators receive no class list and no `plantwild_prompts.json`. Session order is randomized per observer.
- The workbook must contain only `alias, observation, observer_id, observed_at`. The loader rejects any workbook that exposes `image_path`, `sample_id`, `class_id`, `class_name`, `label`, `target`, `split`, or `disease` columns.

## 4. Observation rules

Write 1–3 sentences per image describing **only what is visible**:

- Lesion color, shape, size, margin, surface texture, and distribution; presence of spots, necrosis, chlorosis/halos, powdery or downy coating, wilting, curling, or discoloration.
- The plant organ shown (leaf, stem, fruit) and its visible condition.
- Extent/severity expressed visually (e.g. "a few small spots", "spreads across most of the surface").

Do **not**:

- Name the plant species, crop, or disease (this leaks the target and is rejected by `validate_text_not_label_derived`).
- Copy from any prompt, class list, web page, or model output.
- Invent symptoms not visible in the image, or write generic boilerplate identical across images.
- Use the image's file path, URL, or capture metadata.

Record uncertainty honestly (e.g. "possible early lesion, low confidence"). An empty observation means "not yet annotated"; it is skipped, never filled automatically.

## 5. Schema

**Annotator workbook** (delivered to observers; `data/annotation/annotator_workbook_template.csv`):

| Column | Meaning |
|---|---|
| `alias` | Opaque image handle; no path or label |
| `observation` | Free-text visual observation (verbatim) |
| `observer_id` | Annotator pseudonymous identifier |
| `observed_at` | Date of the observation (ISO 8601) |

**Training CSV** (produced only after review; unchanged six-column schema; `data/annotation/observations_template.csv`):

| Column | Meaning / validation |
|---|---|
| `sample_id` | Must equal the normalized relative `image_path` (loader-enforced; prevents pair misalignment) |
| `image_path` | Relative path under `images/`; must exist in exactly one official split |
| `text` | The approved observation, copied verbatim |
| `text_origin` | `paired_human_observation` for curated offline observations; `user_observation` for inference-time input |
| `provenance` | Collection method, observer pool, date range, instruction version |
| `source_reference` | Stable URI to the annotation record / registry |

Class and split are **not** columns; they are joined from the official split files.

**Review ledger** (`data/annotation/review_ledger_template.csv`), keyed by `sample_id`: `sample_id, review_status, reviewer, reviewed_at, notes`, where `review_status ∈ {pending, approved, rejected, disputed}`. Only `approved` rows are admissible.

## 6. Provenance, identity, and correspondence checks

- **Provenance:** `provenance` must name the collection method and observer pool (≥12 characters, not a placeholder); `source_reference` must be a URL or stable URI. Both are required by the loader.
- **Sample identity:** each observation resolves through the sealed alias map to exactly one eligible `sample_id`; `sample_id` must equal the normalized `image_path`.
- **Image-text correspondence:** one observation per image; the emitted row must pass `ml.fusion.data.load_paired_text_csv` on the real dataset (this also re-checks path safety, split membership, duplicate-image protection, and label-derived text).
- **Coverage:** the emitted CSV is filtered against the eligibility manifest so only eligible samples reach training.

## 7. Validation workflow

```powershell
# 1. Build the blinded workbook + sealed alias map (idempotent; reuses an existing sealed map)
python -m scripts.build_annotation_workbook

# 2. Observers fill observation text; curator compiles the review ledger
#    data/annotation/annotator_workbook_template.csv  ->  filled workbook
#    data/annotation/review_ledger_template.csv       ->  review ledger

# 3. Validate and (only when every row is approved) emit the training CSV
python -m scripts.validate_annotations --workbook <filled.csv> --alias-map outputs/annotation/sealed/alias_map.json `
    --review-ledger <ledger.csv> --text-origin user_observation `
    --instrument-version "<instrument version, e.g. v3.2>" `
    --provenance "<collection method + observer pool + dates + instrument v3.2>" `
    --source-reference <stable-uri> --emit-observations data/paired_observations.csv
```

Without `--emit-observations` the validator reports progress (`INCOMPLETE` / `READY_TO_EMIT`). Emission is blocked unless a review-ledger entry exists for every observation with status `approved`, and the elicitation instrument version is recorded in `provenance`.

## 8. Annotation-quality review (held-out)

- **Blind double annotation:** a held-out subset (recommended ≥5% of eligible images, stratified across classes and splits) is annotated independently by two observers who cannot see each other's text.
- **Agreement metric:** score agreement on the presence and location of symptom features (a small rubric: affected organ, lesion presence, colour, distribution). Compute per-feature agreement and an overall agreement rate; report the held-out agreement before scaling to the full set.
- **Adjudication:** a third, independent adjudicator resolves each disagreement using the image only. The adjudicated text must be one of the two submitted observations or a faithful synthesis of visible features — never new invented content. Disputed rows are resolved to `approved` or `rejected`; unresolved rows stay `disputed` and are excluded from training.
- **Drift control:** if agreement on the held-out subset falls below the agreed threshold, the instructions are revised and re-piloted before the full annotation run. The adjudication records are retained as part of `source_reference` provenance.

## 9. Inference-time availability (decision finalized — Stage 2C)

Curator-written, image-specific observations exist only offline. At deployment a user submits a photo without a hidden caption, so **curator observations are not available at inference**.

**Chosen modality: Option A — user-provided symptom descriptions.** Contributors are briefed as "simulated users" and describe each eligible image (via opaque alias, no labels) through the **same instrument** the production upload form uses. Emitted rows carry `text_origin = user_observation`, and the instrument version is recorded in `provenance`. This is the only modality that (a) matches the existing `paired_text` field on `/api/multimodal/analyze` and (b) keeps train/validation/test/inference text from one distribution.

**Fallback: Option B — blinded curator observations** (`paired_human_observation`) may be used **only** if the study is explicitly scoped as an offline research benchmark, and then it must not claim deployable multimodal inference. The production model stays image-only.

**No mixing.** Option A and Option B text must never be combined in one experiment without a documented protocol proving the two sources are interchangeable for every split; none exists, so mixing is prohibited.

See `text_modality_decision.md` for the full tradeoff analysis and the training gate.

## 10. Exact data requirements before training can start

1. One approved observation for a sufficient subset of each eligible split (train, validation, test), covering all 89 classes in each split.
2. An `approved` review-ledger entry for every emitted observation.
3. A validated `data/paired_observations.csv` (six columns) that passes `load_paired_text_csv` and the eligibility filter.
4. A documented inference-time modality (Section 9) matching the training text source.

Until these exist, fusion and text-only models remain untrained. No synthetic observations may be substituted.
